# 事故档案：2026-10-08 部署后客户端大面积 405（约 50 分钟）

> 上级入口：../SKILL.md。本档案是「协议探针 + 两段式部署」流程的由来，排障思路可复用。

## 现象

13:57 部署（删 `/v1/chat/completions` 的新版本切到 green 槽）后：

- pi 会话 `low-model-auto` 大量 `405 status code (no body)`，重试偶尔成功；
- 其他连接 router 的服务同样 405；
- 持续到 ~14:46 用户才要求紧急回滚。

## 证据链（可复用的定位方法）

1. **会话 JSONL 是第一现场**：`~/.pi/agent/sessions/<...>.jsonl` 里失败 turn 带
   `"api": "openai-completions"`、`"405 status code (no body)"` —— 直接给出客户端协议与时间戳。
2. **405 空 body = 路由层错误**：axum 路由未命中 handler（端点被删后 POST 落到
   `fallback(get(dashboard))`，POST 方法不被允许）→ 请求没进任何 handler，**与 key/上游完全无关**。
3. **时间线对齐**：green 13:57:10 启动，第一条 405 13:57:11.754（差 1.6s），此后持续。
4. **直探分槽对照**（绕过 front-proxy）：`POST /v1/chat/completions` → blue(8790, 旧二进制) = 200，
   green(8791, 新二进制) = 405 → 锁定"新版本删了端点"而非 key。
5. **间歇成功的解释**：front-proxy 只对传输层失败换下一槽，405 原样透传；切流后仍偶有成功
   是 green 传输层抖动时兜底到 blue（旧二进制 chat 完好）——"重试几次后正常"是假象，405 未停止。

## 根因

- 删除客户端协议端点前未做客户端审计：pi 的 `low-model-auto` 在 models.json **模型级**条目
  用 `openai-completions`（provider 级是 `openai-responses`，两层配置不一致导致漏判），
  其他本机服务也走 chat 协议。
- 部署健康检查只有 `/health` + GET 管理 API，POST 协议端点未被探测 → green "healthy" 但协议不可用。

## 处置

- 紧急回滚：`curl -X POST http://127.0.0.1:8789/_proxy/active/blue` —— 秒级恢复，无需重启。
- 流程固化：两段式部署 + `scripts/probe_slot.py` 协议探针（本 skill）。

## 教训清单

1. 客户端协议配置要分层看（provider 级 vs 模型级），删端点前逐客户端确认。
2. "重试后正常"不等于恢复——要看错误是否还在新增（会话 JSONL / errors/recent）。
3. 405/404 先查协议端点匹配，再查 key；空 body 的 4xx 基本可断定没进 handler。
4. 部署探针必须用客户端真实的方法+路径（POST 协议端点），GET 管理 API 探不出协议破坏。
